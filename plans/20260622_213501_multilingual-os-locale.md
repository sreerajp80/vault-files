# Plan: Make Vault Files multi-lingual (follows Android OS language)

## Goal / requirement

Make the app multi-lingual so the UI text adheres to the **Android OS language**.
Target languages for this round:

- **English (en)** — default, lives in `res/values/strings.xml`.
- **Malayalam (ml)** — `res/values-ml/strings.xml`, translations generated by Claude
  (user will review them).

Android automatically resolves `values-<lang>` from the device locale at runtime, so **no
runtime locale-switching code is required** to "follow the OS language." The work is almost
entirely string externalization + providing a translated copy.

## What the issue is

The app has effectively **no string externalization**:

- `res/values/strings.xml` contains only `app_name`.
- All user-facing text (~150+ literals) is hardcoded in the Kotlin/Compose source across
  the 6 UI files, plus user-notification messages built with string templates in
  `StorageViewModel`.

Because the strings are baked into code, the OS locale has nothing to switch to. We must move
every user-facing string into resources and reference them via `stringResource()` (Compose) or
`getString()` (ViewModel).

## Files to be changed

### Resource files
1. `app/src/main/res/values/strings.xml` — **(edit)** add all extracted English strings
   (named, grouped by screen).
2. `app/src/main/res/values-ml/strings.xml` — **(new)** Malayalam translations of every key,
   same `name` set as the default file.

### Kotlin source (replace literals with resource lookups)
3. `app/src/main/java/com/example/MainActivity.kt`
4. `app/src/main/java/com/example/ui/StorageAnalyzerScreen.kt`
5. `app/src/main/java/com/example/ui/FileExplorerScreen.kt`
6. `app/src/main/java/com/example/ui/SettingsScreen.kt`
7. `app/src/main/java/com/example/ui/SecureVaultScreen.kt`
8. `app/src/main/java/com/example/ui/AboutScreen.kt`
9. `app/src/main/java/com/example/ui/StorageViewModel.kt` — messages via
   `getApplication<Application>().getString(R.string.x, args...)` (it is an `AndroidViewModel`,
   so a Context is available).

### Build config (optional, low risk)
10. `app/build.gradle.kts` — add `androidResources { generateLocaleConfig = true }` and a
    `<locale-config>` reference so the app advertises its supported languages to the system
    (enables the per-app language setting in Android 13+). Strictly optional for "follow OS
    language," but recommended. Will confirm before touching the build file.

## Plan for the fix

1. **Inventory & name the strings.** Go screen by screen, collect every user-facing literal
   (button labels, titles, content descriptions, dialog text, snackbar/toast messages). Assign
   stable, grouped resource names, e.g. `settings_title`, `vault_unlock_button`,
   `msg_folder_created`, `cd_back` (content descriptions prefixed `cd_`).

2. **Handle parameterized messages.** Templates like
   `"Folder created successfully: $name"` become positional-format resources:
   `<string name="msg_folder_created">Folder created successfully: %1$s</string>` and are read
   with `getString(R.string.msg_folder_created, name)`. Boolean-driven phrasing (e.g.
   "enabled"/"disabled") is split into two resources or a sub-string the caller selects, so the
   sentence stays grammatical in Malayalam.

3. **Populate `values/strings.xml`** with the English defaults.

4. **Replace literals in code:**
   - Compose: `Text("Settings")` → `Text(stringResource(R.string.settings_title))`; add
     `import androidx.compose.ui.platform.stringResource` and `import com.example.R` where
     needed. `LocalContext`/`stringResource` already imported in most UI files.
   - `StorageViewModel`: literals → `getString(...)`.

5. **Create `values-ml/strings.xml`** with Malayalam translations for every key (matching the
   default `name` set 1:1). User reviews these.

6. **Leave non-UI strings alone:** demo/seed data file names and internal canonical keys in
   `StorageRepository`/`StorageViewModel` (e.g. category keys `"Image"`, mode `"sandbox"`,
   theme `"system"`) are **not** translated — only the labels actually shown to the user are.
   Where a canonical key is currently shown directly as a label, map it to a `stringResource`
   at display time.

7. **Verify:** `./gradlew assembleDebug` to confirm it compiles; spot-check that no user-facing
   literal remains (Android Studio's "hardcoded string" lint / a grep pass). Optionally run the
   app with the device set to Malayalam to confirm switching.

## Notes / decisions already made
- Languages: English (default) + Malayalam. Translations generated by Claude; **user will
  review** them.
- No in-app language picker is being added — strictly follows the OS locale, as requested.
- minSdk 24 / targetSdk 36 — default resource resolution covers all of these; no compat shims
  needed.

## Out of scope
- Real localization of demo/seed data and internal keys.
- RTL layout work (Malayalam is LTR; not applicable).
- Date/number/plural locale formatting beyond what `getString`/positional args already give.
